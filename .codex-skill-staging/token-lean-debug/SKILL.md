# Token Lean Debug

debug 的目標不是讀更多，而是更快縮小 bug surface。

## 核心原則

1. 先拿症狀，再找入口。
2. 先證明哪裡沒壞，再逼近哪裡壞了。
3. 只追一條最可能的 call path，不同時展開多條支線。
4. 沒有證據前，不做大改。

## Debug 流程

1. 用一句話重述症狀。
2. 抽出一個可驗證的假設。
3. 找唯一入口或最接近症狀的函式。
4. 向前或向後追 1 到 2 層呼叫鏈。
5. 在最小位置修復。
6. 跑最小驗證確認症狀是否消失。

## 讀檔限制

- 不先讀整個 feature。
- 不先讀整份 state management 或整包 networking。
- 每次只新增一個必要檔案到上下文。
- 若已確認某層正常，就不要重讀那層。

## 對錯誤訊息的處理

- 報錯很長時，只保留：
  - 錯誤型別
  - 第一個業務相關堆疊位置
  - 最後一個使用者程式碼位置
- 若日誌很多，只抓第一次異常與最接近根因的前後文。

## 修復策略

- 優先選擇能阻止錯誤重現的最小修復。
- 如果根因尚未完全確定，先避免做結構性重寫。
- 若需要防禦式處理，說清楚它是在補保護還是在修根因。

## 驗證策略

- 先驗症狀是否消失。
- 再驗最可能被影響的相鄰路徑。
- 不預設跑全量測試，除非修改面已經擴大。
- 若任務在 Android 或 iOS 端，預設不主動編譯、打包、安裝或跑完整測試，除非使用者明確要求。

## 回報格式

只保留這些資訊：

- 症狀
- 假設
- 根因
- 修復
- 驗證
- 剩餘風險

## 內部短句

- 「先縮面，不先解釋整個系統。」
- 「現在只追這一條 call path。」
- 「先證明根因，再決定是否擴修。」
